## 三、中断处理流程

### 3.1 arm架构对中断的处理步骤

① 初始化：

​	a) 设置中断源，让它可以产生中断

​	b) 设置中断控制器(可以屏蔽某个中断，优先级)

​	c) 设置 CPU 总开关(使能中断)

② 执行其他程序：正常程序

③ 产生中断：比如按下按键--->中断控制器--->CPU

④ **CPU 每执行完一条指令都会检查有无中断/异常产生**

⑤ CPU 发现有中断/异常产生，开始处理。

​	对于不同的异常，跳去不同的地址执行程序。

​	这地址上，只是一条跳转指令，跳去执行某个函数(地址)，这个就是异常向量。**其中③④⑤都是硬件做的**。

⑥ 这些函数做什么事情？

​	软件做的:

​		a) 保存现场(各种寄存器)

​		b) 处理异常(中断):分辨中断源，再调用不同的处理函数

​		c) 恢复现场



### 3.2 异常向量表

在uboot或者linux内核代码中，通常有以下代码：

```assembly
_start: b reset
	ldr pc, _undefined_instruction
	ldr pc, _software_interrupt
	ldr pc, _prefetch_abort
	ldr pc, _data_abort
	ldr pc, _not_used
	ldr pc, _irq //发生中断时，CPU 跳到这个地址执行该指令 **假设地址为 0x18**
	ldr pc, _fiq
```

这就是异常向量表，每一条指令对应一种异常。

发生复位时，CPU 就去 执行第 1 条指令：b reset。

发生中断时，CPU 就去执行“ldr pc, _irq”这条指令。

这些指令存放的位置是固定的，比如对于 ARM9 芯片中断向量的地址是0x18。

当发生中断时，CPU 就强制跳去执行 0x18 处的代码。



注：

1、其中fiq是快速中断，它和irq的差别如下：

| **特性**       | **IRQ（普通中断）**              | **FIQ（快速中断）**                      |
| :------------- | :------------------------------- | :--------------------------------------- |
| **优先级**     | 较低，可以被 FIQ 抢占            | 最高，可抢占 IRQ                         |
| **中断屏蔽**   | 可通过 CPSR 的 **I-bit** 屏蔽    | 默认不可屏蔽（除非改 **F-bit**）         |
| **寄存器**     | 使用通用寄存器，需手动保存上下文 | 有专用寄存器（r8-r14_fiq），减少保存开销 |
| **中断源共享** | 通常多个设备共享一个 IRQ         | 通常独占，避免冲突                       |
| **向量表位置** | `0x18`                           | `0x1C`（可紧接 FIQ 处理代码）            |
| **延迟**       | 较高（需保存较多寄存器）         | 极低（专用寄存器+优化跳转）              |
| **典型应用**   | 通用外设（UART、定时器等）       | 超低延迟任务（DMA、实时控制）            |



2、向量表的位置并不总是从 0 地址开始，很多芯片可以设置某个vector base 寄存器，指定向量表在其他位置，比如设置 vector base 为0x80000000，指定为 DDR 的某个地址。但是表中的各个异常向量的偏移地址，是固定的：复位向量偏移地址是 0，中断是 0x18。

### 5.1  arm处理器程序运行的过程

ARM 芯片属于精简指令集计算机(RISC：Reduced Instruction Set Computing)，它所用的指令比较简单，有如下特点：

​	① 对内存只有读、写指令

​	② 对于数据的运算是在 CPU 内部实现

​	③ 使用 RISC 指令的 CPU 复杂度小一点，易于设计

如上，执行以下操作：

- 先对程序A的cpu寄存器数据进栈，保存在程序A的栈中，此时程序A的内存空间中有栈、data段、代码段等数据；
- 恢复程序B的现场，也就是从程序B的栈中读取寄存器的值，恢复到cpu寄存器中；
- 取程序B的代码执行；

在程序B的代码执行完之后，再进行恢复，如下：

 ![image-20250520174756939](E:\embedded_learning\embedded_driver_code_management\src\007_button_irq\image-20250520174756939.png)

- 将cpu寄存器的值保存进程序B的栈中；
- 从程序A的栈中将数据读出来，恢复到CPU寄存器中，也就是恢复现场；
- 从程序A的代码段继续取机器码执行；
- 最后执行程序A剩下的代码；



注：

以上的流程，在函数中嵌套执行其他函数时，也会执行与中断类似的工作，即：

- 函数A中保存现场
- 执行函数B;
- 恢复现场继续执行程序A；

① 软件中断何时生产？

​	由软件决定，对于 X 号软件中断，只需要把它的 flag 设置为 1 就表示发生了该中断。

② 软件中断何时处理？

​	软件中断紧急度并不高，有空再处理它。

​	什么时候有空？不能让它一直等吧？

​		Linux 系统中，各种硬件中断频繁发生，至少定时器中断每 10ms 发生一次；

​	综上规定：

​		在处理完硬件中断后，再去处理软件中断；





#### 5.4.2 中断上半部和下半部

中断的处理遵循以下原则：

- 硬件中断不能嵌套
- 中断响应函数必须简洁，不能耗时太久



对于中断耗时部分的处理，通常有以下方法：

- **分为进程上半部和下半部**。上半部由硬件中断触发，该中断处理期间不会被打断；下半部由软件中断触发，这个中断处理在硬件中断执行完之后顺便执行，可以被其他中断打断；
- 将耗时部分放在内核线程中处理，中断处理函数仅进行标志的设置；

![image-20250521110753776](E:\embedded_learning\embedded_driver_code_management\src\007_button_irq\image-20250521110753776.png)

中断上下半部的调度流程：

![image-20250521122811154](E:\embedded_learning\embedded_driver_code_management\src\007_button_irq\image-20250521122811154.png)

上述代码的设计，会导致中断上半部可能执行多次，而中断下半部只执行一次，原因是：

- 如果preempt_count走到第五步时，preempt_count被累加为1；
- 在第五步和第八步之间，发生了硬中断都有可能打断中断下半部的执行，导致cpu又会开始从第一步开始执行；
- 因为第四步的判断，除了第一次中断，后续的中断都无法进入到中断下半部的流程里；

最终导致**上半部和下半部执行次数为N : 1**；

#### 5.4.4 工作队列

如果中断要做的事情实在太耗时，那就不能用软件中断来做，而应该用内核线程来做：在中断上半部唤醒内核线程。内核线程和APP 都一样竞争执行，APP 有机会执行，系统不会卡顿。

这个内核线程是系统帮我们创建的，一般是 kworker 线程，内核中有很多这样的线程：

![image-20250521163935008](E:\embedded_learning\embedded_driver_code_management\src\007_button_irq\image-20250521163935008.png)



kworker 线程要去“工作队列”(work queue)上取出一个一个“工作”(work)，来执行它里面的函数。

使用工作队列的方法：

- 创建work，例如：

  ```c
  // 结构体原型
  struct work_struct {
  	atomic_long_t data;
  	struct list_head entry;
  	work_func_t func;
  #ifdef CONFIG_LOCKDEP
  	struct lockdep_map lockdep_map;
  #endif
  };
  
  // iucv_work为要创建的结构体的名称，iucv_work_fn为绑定该work的函数
  static DECLARE_WORK(iucv_work, iucv_work_fn);
  ```

- 想要work被执行，调用schedule_work函数，如下：

  ```c
  static inline bool schedule_work(struct work_struct *work)
  {
  	return queue_work(system_wq, work);
  }
  ```

  这个函数会把work加入到work_queue中去，然后回随着工作队列竞争cpu资源，来获得执行的机会；



#### 5.4.5 总结

- 很耗时的中断处理，应该放到线程里去

- 可以使用 work、work queue

- 在中断上半部调用 schedule_work 函数，触发 work 的处理

- 既然是在线程中运行，那对应的函数可以休眠。



### 5.5 新技术——thread irq

#### 5.5.1 函数原型

```c
int request_threaded_irq(unsigned int irq, irq_handler_t handler,
			 irq_handler_t thread_fn, unsigned long irqflags,
			 const char *devname, void *dev_id);
```



#### 5.5.2 函数功能

`request_threaded_irq()` 用于**注册一个线程化中断（threaded IRQ）**，它允许中断处理分为两部分：

1. **硬中断（`handler`）**：在中断上下文中执行（要求快速完成）。
2. **线程化中断（`thread_fn`）**：在内核线程中执行（可以睡眠、调度）。

相比 `request_irq()`，它更适合**处理耗时中断**（如 I/O 操作、等待锁等）。



#### 5.5.3 参数说明

| 参数        | 类型            | 说明                                                        |
| :---------- | :-------------- | :---------------------------------------------------------- |
| `irq`       | `unsigned int`  | 中断号（如 `IRQ_GPIO`）                                     |
| `handler`   | `irq_handler_t` | **硬中断处理函数**（返回 `IRQ_WAKE_THREAD` 触发线程化处理） |
| `thread_fn` | `irq_handler_t` | **线程化中断处理函数**（在单独的线程中运行）                |
| `flags`     | `unsigned long` | 中断标志（如 `IRQF_ONESHOT`、`IRQF_SHARED`）                |
| `name`      | `const char *`  | 中断名称（`/proc/interrupts` 显示）                         |
| `dev`       | `void *`        | 传递给 `handler` 和 `thread_fn` 的设备指针                  |

#### 5.6.2 irqaction 结构体

```c
// include/linux/interrupt.h
/**
 * struct irqaction - per interrupt action descriptor
 * @handler:	interrupt handler function
 * @name:	name of the device
 * @dev_id:	cookie to identify the device
 * @percpu_dev_id:	cookie to identify the device
 * @next:	pointer to the next irqaction for shared interrupts
 * @irq:	interrupt number
 * @flags:	flags (see IRQF_* above)
 * @thread_fn:	interrupt handler function for threaded interrupts
 * @thread:	thread pointer for threaded interrupts
 * @secondary:	pointer to secondary irqaction (force threading)
 * @thread_flags:	flags related to @thread
 * @thread_mask:	bitmask for keeping track of @thread activity
 * @dir:	pointer to the proc/irq/NN/name entry
 */
struct irqaction {
	irq_handler_t		handler;
	void			*dev_id;
	void __percpu		*percpu_dev_id;
	struct irqaction	*next;
	irq_handler_t		thread_fn;
	struct task_struct	*thread;
	struct irqaction	*secondary;
	unsigned int		irq;
	unsigned int		flags;
	unsigned long		thread_flags;
	unsigned long		thread_mask;
	const char		*name;
	struct proc_dir_entry	*dir;
} ____cacheline_internodealigned_in_smp;
```

当调用 request_irq、request_threaded_irq 注册中断处理函数时，内核就会构造一个 irqaction 结构体。在里面保存 name、dev_id 等，最重要的是 handler、thread_fn、thread。

handler 是中断处理的上半部函数，用来处理紧急的事情。

thread_fn 对应一个内核线程 thread，当 handler 执行完毕，Linux 内核会唤醒对应的内核线程。在内核线程里，会调用 thread_fn 函数。

- 可以提供 handler 而不提供 thread_fn，就退化为一般的 request_irq 函

数。

- 可以不提供 handler 只提供 thread_fn，完全由内核线程来处理中断。

- 也可以既提供 handler 也提供 thread_fn，这就是中断上半部、下半部。



在 reqeust_irq 时可以传入 dev_id，为何需要 dev_id？作用有 2：

① 中断处理函数执行时，可以使用 dev_id

② 卸载中断时要传入 dev_id，这样才能在 action 链表中根据 dev_id 找到对应项

所以在**共享中断中必须提供 dev_id，非共享中断可以不提供**


它表示要使用 gpio1 里的第 5 号中断，hwirq 就是 5。

而在驱动中，我们需要通过request_irq(irq, handler)这样的函数来注册中断，irq是虚拟中断号(理解为虚拟中断号更好，与软中断和硬中断区分开)，这个虚拟中断号就是从设备树中的信息（“gpio1 的第 5 号中断”）转化而来的；而负责转化的就是对应的irq_domain结构体；

irq_domain 结构体中有一个 irq_domain_ops 结构体，里面有各种操作函数，主要是：

- xlate：用来解析设备树的中断属性，提取出 hwirq、type 等信息。

- map：把 hwirq 转换为 irq。



#### 5.6.5 irq_chip结构体

```c
// include/linux/irq.h
/**
 * struct irq_chip - hardware interrupt chip descriptor
 *
 * @parent_device:	pointer to parent device for irqchip
 * @name:		name for /proc/interrupts
 * @irq_startup:	start up the interrupt (defaults to ->enable if NULL)
 * @irq_shutdown:	shut down the interrupt (defaults to ->disable if NULL)
 * @irq_enable:		enable the interrupt (defaults to chip->unmask if NULL)
 * @irq_disable:	disable the interrupt
 * @irq_ack:		start of a new interrupt
 * @irq_mask:		mask an interrupt source
 * @irq_mask_ack:	ack and mask an interrupt source
 * @irq_unmask:		unmask an interrupt source
 * @irq_eoi:		end of interrupt
*/

struct irq_chip {
	struct device	*parent_device;
	const char	*name;
	unsigned int	(*irq_startup)(struct irq_data *data);
	void		(*irq_shutdown)(struct irq_data *data);
	void		(*irq_enable)(struct irq_data *data);
	void		(*irq_disable)(struct irq_data *data);

	void		(*irq_ack)(struct irq_data *data);
	void		(*irq_mask)(struct irq_data *data);
	void		(*irq_mask_ack)(struct irq_data *data);
	void		(*irq_unmask)(struct irq_data *data);
	void		(*irq_eoi)(struct irq_data *data);

	// 省略不常用的方法...

	unsigned long	flags;
};
```

这个结构体提供了一些芯片级的方法，用来操作中断，比如使能，关闭中断等；

## 七、调试总结

- 如果设备树中共用了某个gpio作为中断，就会导致中断注册时报错，例如我注册的KEY2与设备树中已有的usr_button1冲突：

  ```
  genirq: Flags mismatch irq 82. 00000002 (KEY2) vs. 00000081 (usr_button1)
  ```

  设备树语句冲突如下：

  新节点

  ```dtd
  100ask_btns {
                  compatible = "100ask,button_dtb_drv";
                  #address-cells = <1>;
                  #size-cells = <0>;
  
                  button@0 {
                          num = <1>;
                          button-gpios = <&gpiog 3 GPIO_ACTIVE_LOW>;
                          label = "KEY1";
                          interrupt-parent = <&gpiog>;                // 指向 GPIOG 中断控制器
                          interrupts = <3 IRQ_TYPE_EDGE_BOTH>;        // 引脚3, 双边沿触发
                  };
  
                  button@1 {
                          num = <2>;
                          button-gpios = <&gpiog 2 GPIO_ACTIVE_LOW>;
                          label = "KEY2";
                          interrupt-parent = <&gpiog>;                // 指向 GPIOG 中断控制器
                          interrupts = <2 IRQ_TYPE_EDGE_BOTH>;        // 引脚2, 双边沿触发
                  };
          };
  ```

  已有节点：

  ```dtd
  //在stm32mp15xx-100ask.dtsi中
  joystick {
  	        compatible = "gpio-keys";
          	#size-cells = <0>;
          	button-0 {
                 		 label = "usr_button0";
                 		 linux,code = <KEY_A>;
                  	interrupt-parent = <&gpiog>;
                  	interrupts = <3 IRQ_TYPE_EDGE_RISING>;
          	};
                 button-1 {
                           label = "usr_button1";
                           linux,code = <KEY_ENTER>;
                          interrupt-parent = <&gpiog>;
                          interrupts = <2 IRQ_TYPE_EDGE_RISING>;
                  };
  
  	};
  ```

- 在设备树中声明中断，尽可能声明清楚interrupt-parent和interrupts

  ```dtd
  button@0 {
                          num = <1>;
                          button-gpios = <&gpiog 3 GPIO_ACTIVE_LOW>;
                          label = "KEY1";
                          interrupt-parent = <&gpiog>;                // 指向 GPIOG 中断控制器
                          interrupts = <3 IRQ_TYPE_EDGE_BOTH>;        // 引脚3, 双边沿触发
                  };
  ```

- 在probe函数中申请的资源，如内存、中断等，在remove函数中应该进行相应的释放；
